# 资料、范围与内容架构

用于新建、整体改版，以及用户指出“信息不对、内容缺失、看不懂这个区块”的任务。

## 1. 判断网站要完成什么任务

先确认最影响方案的五项：目标访客、核心动作、页面范围、现有资产、当前交付阶段。已有对话能回答的不要再次询问。

最小输入是用户已经有的内容，不是五项齐备的表单。先读取附件、链接和品牌介绍并代为提炼：明确说“做网页”时推进到实现；单一产品且内容不多可先拟一页结构；已有 repo 沿用其栈；没有参考可从品牌与行业推导视觉方向。这些实现假设可以先执行并简短说明，涉及商业承诺的未知信息保留待补。

| 类型 | 需要优先解决的问题 | 常见路径 |
| --- | --- | --- |
| 品牌官网 | 是谁、提供什么、为何可信、如何联系 | 认识品牌 → 理解业务 → 查看证据 → 联系 |
| 独立站 / B2B 询盘 | 产品是否合适、能否定制、采购如何进行 | 分类 → 产品 / 规格 → 采购保障 → 询盘 |
| SaaS 官网 | 为谁解决什么问题、如何工作、成本与下一步 | 场景 → 真实产品与结果 → 价格 → 登录 / 留资 |

独立站不自动等于在线商城；购物车、支付、订单和履约只在本次范围需要时加入。单页、多页由任务和内容量决定，不因“完整网站”擅自增加页面。

列出必须保留项，如原有标识、绿色优势区、采购步骤、真实登录方式、已有 folder。将“界面优化”与“新增业务能力”分开，发现缺口时说明差异和可实现路径。

## 2. 按内容用途建立依据

按需读取：

- 需求文档的正文、表格、截图、图片注释及备注；检查折叠区域与关联材料。
- 现有站点、实际产品、代码和相关 PR，区分已有行为与未来规划。
- 现有设计稿及用户手调后的节点、文字样式、素材、断点。
- 商家官网、店铺或资料包中的产品、场景、供应链照片、联系方式和背书。

用简表记录有争议或容易混淆的信息：

| 信息 | 依据 | 用于哪里 | 状态 |
| --- | --- | --- | --- |
| 套餐额度 | 已确认的需求文档 | 官网价格展示 | 文案已定；运行时额度另核对 |
| 产品图 | 商家原始素材 | 分类与详情 | 已选定；需核对分类 |
| 供应商审核 | 可查看的报告 | About / 信任证据 | 记录主体、日期和适用范围 |

用户最新明确纠正优先；但要区分事实领域：营销文档可以决定已授权的展示文案，实际接口和代码决定当前能运行的行为。二者冲突时标明差异，不为了让文案成立而暗改产品额度、计费或权限。

删除线、候选文案和旧截图如果会改变方案，需要核对含义。用户给出的原始来源能查到的信息先查，不把“未阅读”当成“用户没提供”。

## 3. 盘点素材与可信度

- 记录素材用途、来源、版本、清晰度、比例和使用限制；已有 Logo 优先使用确认版本。
- 分类图片要能区分产品，不能仅因配色一致就选择相似场景。
- 图片增强后核对产品形态、颜色和细节；生成式修复结果不能充当规格或品质证据。
- 供应商评估、产品认证、奖项和合作关系分别表述，展示可核验的主体与范围。
- 发现占位证书文字或相互矛盾的规模数字时，先采用可确认内容，不补造数据。
- 缺失社媒、二维码、视频或接口可以继续做布局和接入点，记录待补项；不编造真实联系方式。

已有 PPT、官网或设计稿里的处理后照片、Logo 组合与场景截图同样是可复用素材。不要只提取原始文件而丢掉用户认可的蒙版、裁切和光效；先确认需要沿用的是哪个成品版本。Logo 可以用于身份识别，不代表已允许拿它反复做背景装饰；用途变化需依据当前任务。

需要 Logo 重设计或 IP 制作时，说明它属于独立任务；本流程继续处理已确认资产的接入。

## 4. 将信息组织成页面

对每个 section 回答：

1. 访客此时有什么问题？
2. 一句标题、简短说明和什么证据能回答？
3. 需要什么画面，能否来自真实产品或素材？
4. 看完可以做什么，是否需要 CTA？
5. 与前后区块有无重复，能否合并而不损失必要信息？

独立站常见区块包括首屏、产品分类、应用场景、定制能力、供应链与公司介绍、采购流程、FAQ 和询盘；SaaS 常见区块包括首屏、业务场景、产品工作方式、结果与背书、价格、教程、FAQ 和留资。它们是候选内容，不是每站必须套用的顺序。

## 5. 写清楚文案

- 分类与功能区优先使用明确名称，避免只有漂亮但无法识别内容的标题。
- 用用户问题、产品动作和可见结果组织说明，去掉重复角标、无意义小字与空泛口号。
- 简化时保留采购步骤中的必要解释、用户强调的区块和有依据的信任信息。
- 产品画面承担解释时，正文不必重复画面里所有字段。
- 同一价格、计划名和产品名在页头、正文、FAQ、footer 及登录页之间保持一致。
- 对未开放能力说明当前状态，不把“未来可以”写成“现在可用”。

将抽象问题改成具体表达：

| 发现的问题 | 操作 | 验收 |
| --- | --- | --- |
| 产品区标题只讲 beautiful，访客不知道是什么 | 改成能识别主产品 / 分类的标题，去掉与标题同义的角标 | 不看解释也能知道这里浏览产品 |
| 场景区有很多零碎小字 | 每个场景保留任务、动作与结果，剩余信息交给真实 UI 画面 | 场景之间能快速比较，不必逐行读小标签 |
| slogan 断成多个宣传短语或带生硬标签 | 写成自然的一句话，明确产品对象或实际作用；品牌词保持一致 | 首页、登录和 footer 同义，按宽度自然换行 |
| About 过长，精简后又丢了信任证据 | 短介绍 + 关键点 + 制作 / 供应链照片及可核验资料；去重说明 | 用户指定的优势区、采购步骤和有效背书仍在 |

证书或报告图片需要裁掉装饰奖杯时，只裁展示区域并保留必要的主体、正文与可读性；不重绘认证内容、不将供应商审核改写为产品认证。

## 输出与验收

输出足以推进下一步的 brief、内容结构与素材缺口。检查原始资料中的每个相关需求是否有落点，访客能否从标题理解区块用途，所有关键 CTA 是否已有明确去向。只请求真正影响方案的剩余信息。
