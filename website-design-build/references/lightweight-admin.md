# 轻量后台

用于品牌方维护产品、页面内容和询盘。以本次需要的最小闭环为范围；不默认扩展自由拖拽建站器、多租户 CRM 或复杂权限平台。

## 1. 先确认前台与数据现状

检查现有分类、产品、页面内容、表单、图片和发布方式。确认内容是写在代码、构建生成、运行时查询还是已有 CMS 管理。

后台语言、管理员身份和日常操作按使用者决定。品牌公开邮箱、内部管理员邮箱和询盘客户邮箱分别存放。已有登录优先复用；确需新管理员登录时按项目支持的方式实现，不硬编码历史项目的用户名或个人邮箱。

| 模块 | 适合第一版的能力 | 与前台的关系 |
| --- | --- | --- |
| 产品分类 | 名称、介绍、封面、排序 | 分类卡片与分类介绍 |
| 具体产品 | 图片、名称、分类、描述、规格、状态 | 对应分类下的产品列表与详情 |
| 页面内容 | 按 section 修改文案、图片、FAQ、联系方式 | 保留设计结构的内容替换 |
| 询盘 | 查看详情、状态、内部备注、必要的导出 | 网站提交的真实记录 |
| 管理员 | 登录、退出、必要的密码管理 | 受保护的编辑与数据读取 |

不要为后台自由度牺牲已确认的前台设计；按 section 填写通常足够，字段按本项目内容选取。

## 2. 定义内容状态

至少区分相关的草稿、已发布和归档 / 下架。明确：

- 保存草稿是否改变前台；通常不改变。
- 预览是否只对合适的使用者可见。
- 发布的版本与编辑中的版本怎样对应。
- 已发布内容再编辑时，旧正式内容是否继续展示。
- 产品和页面内容分别如何发布，是否需要构建或缓存更新。
- 下架、归档和删除是否可恢复，界面表述是否一致。

数据模型保留稳定分类标识，避免名称改动导致产品丢失归属。需要处理并发编辑时提供版本检查或冲突提示，不为单人后台默认引入复杂协作系统。

## 3. 产品与图片管理

表单包含本项目所需的名称、分类、描述和规格；MOQ、材质、颜色等只对相关业务展示。图片上传需要实际持久存储，不只保留本地文件路径或临时预览地址。

处理保存中、上传失败、图片移除、排序和发布结果。浏览器上传工具不可用时可用允许的接口方式验证存储，但不能因此声称文件选择器的 UI 已测过。

前台打开分类时：有已发布产品就提供可发现的列表；空分类不展示无效引导；详情有返回原分类的路径。后台“发布到哪里”应能用清楚语言解释，并实际验证。

## 4. 内容编辑与预览

保留已确认的布局和视觉 token，将允许编辑的内容映射到稳定字段。记录哪些字段跨语言共享、哪些按语言分别编辑。

核对 HTML 实体、换行、空值和特殊字符不会出现双重转义或破坏页面。FAQ、社媒和图片应有适当的空状态，不把空字符串渲染成失效链接或破图。

## 5. 询盘与跟进

网站提交成功后，后台能找到对应记录，客户联系方式与产品上下文完整。状态和内部备注保存后刷新仍在；内部备注不进入公共响应。

搜索、筛选、分页和导出按实际需求实现。网页邮箱、邮件应用和复制地址的入口核对目标，不把“打开回复页面”视为已发送。

## 6. 最小权限与可靠性

公开访问只获得已发布内容和允许的提交能力；管理员读写及询盘查看在服务端验证，不能只隐藏前端按钮。新建登录需采用可靠的密码散列与会话机制，优先使用项目成熟方案。

按风险处理输入校验、上传限制、重复提交、敏感数据返回和跨站请求。只扩展本次后台所需能力，不把普通建站自动扩展成全面安全审计。

数据库、对象存储、函数与前台部署可以分开提供。选型优先现有账号、维护成本和地区可用性；用户希望沿用现有平台时，先核对该平台集成方案，不强制迁移供应商。

## 7. 验收完整路径

在允许的测试环境：

1. 管理员登录，确认未登录访问受保护接口被拒绝。
2. 新建带明显测试标识的产品，保存草稿，确认公共页面不显示。
3. 发布后从真实前台分类进入列表与详情，再返回分类。
4. 修改内容并预览，发布后核对前台实际数据源和缓存。
5. 提交测试询盘，在后台查看、更新跟进状态并刷新确认保存。
6. 按约定归档或保留测试数据，记录结果。

若 UI、接口、数据库或正式环境只验证了部分，分别报告。不要仅凭“接口返回成功”承诺所有前台已更新。
