# 多语言与区域版本

用于同站多语言、独立地区站点，以及它们关联的价格、登录与部署。不要将语言差异自动等同于数据和账户差异。

## 1. 先建立版本矩阵

只列项目实际需要的维度：

| 维度 | 需要明确的内容 |
| --- | --- |
| 页面 | 首页、价格、登录及其他本次页面 |
| 语言 | 支持语言、默认值、用户选择和回退 |
| 地区 | 域名、部署平台、数据位置、联系渠道 |
| 账户 | 已有认证、共享或独立账号、会话边界 |
| 交易 | 套餐、币种、实际支付或待接入方案 |
| 素材 | 字标、字体、社媒、截图与法律信息 |

共享设计意味着视觉规则和交互保持对应，不意味着 footer、价格、社媒和登录方式必须完全相同。

## 2. 明确语言解析规则

沿用产品既有策略；需要新增时，确定显式选择、账户偏好、URL、浏览器语言与回退的优先级。只在项目要求时自动按系统语言显示。

固定中文的地区域名可以覆盖通用语言识别；国际站可支持多语言并设置回退。移除语言选择器时，仍检查已有显式链接、登录回跳与导航不会丢失语言。

选择器若保留，优先复用现有设计系统组件；手机上是否收入菜单按设计确定。

## 3. 同步内容与布局

- 中文、英文和其他语言使用对应文案，避免只翻译首页主标题。
- 标题、按钮、Tab、FAQ、价格说明、footer、登录和错误消息都在本次覆盖范围内。
- 英文更长或中文字体不同会改变尺寸，用实际文字检查，不能按中文固定坐标复制。
- 字体按角色记录：中文、英文标题、英文 UI、字标；保留用户最新确认的修改。
- 共享 UIUX 修改覆盖相应语言，同时保留各地区已确认的内容差异。
- 品牌 Logo 组合、favicon、公开联系方式和社媒检查各自正确版本。

同一视觉修正至少核对“相关语言 × 对应页面 × 已设计断点”。例如修 FAQ 既看首页也看价格页；改登录左侧既看中文也看英文；改角色图既看原稿也看手机裁切。地区 footer 的社媒与产品链接单独映射，不把中文渠道整组复制到国际站。系统语言策略不等于只支持中英文，沿用现有支持范围及回退规则。

## 4. 日期与原生控件

原生日期控件可能跟随浏览器或系统语言；页面 lang 不一定控制它的全部 UI。产品要求固定语言日历时，优先使用项目已有的本地化日期组件；确需自定义时补齐键盘、焦点、换月、清空和关闭。

区分纯日期与时间戳。选择的到货日期在字段、摘要和提交数据中保持一致，避免用 UTC 转换造成日期偏移。测试日期应相对于当前日期选取，不能复制旧项目某一天作为永久用例。

## 5. 地区、账户和部署

先确认实际域名、认证服务、回调与会话模型。共享品牌或同属一个母域并不证明已实现免登录；需要核对 cookie 作用域、认证后端与允许的回跳。

地区独立登录时，沿用该地区已有功能。国际站需要共享账户时，在真实允许的域名验证登录与会话；随机预览域名不能完整证明正式跨域行为。

国内与国际部署可以共享 UI 实现，再通过配置切分数据、支付和渠道；也可以按项目结构分应用。是否拆两个 PR 依据依赖与交付节奏决定，不把历史项目的拆分方式作为固定要求。

## 验收

选取相关的页面 × 语言 × 设备 × 状态检查。先覆盖主要语言的核心流程，再对共享修改验证其他语言有无布局与行为回归。

记录已验证域名和环境，检查跨站入口、footer 返回母站、登录后目标及社媒差异。明确 UI 翻译、认证共享和地区部署各自是否完成。
