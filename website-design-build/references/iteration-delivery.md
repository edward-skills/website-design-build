# 反馈同步、验收与交付

用于多轮修改、用户手调设计、PR 预览、部署和交接。记录依附现有 issue、PR 或项目文档；小改动不增加成套流程文档。

## 1. 接收反馈时先定位版本

确认反馈对应页面、设计节点、语言、设备和预览版本。用户看到旧部署时先查版本，不立即在新代码重复修同一问题。

将每条反馈分成：内容 / 素材、视觉、布局、交互、业务接口、数据发布、环境 / 部署。明确影响范围与应保留项；最新纠正替代相冲突旧要求，其他约束继续有效。

用户说“保持这个形状，只让内部颜色流动”时，不继续沿用先前的整体旋转方案。用户说“精简文字”时，不自动删除仍需保留的优势区和必要步骤。

## 2. 读取用户手调后的真实稿

获取最新节点与渲染，检查改过的尺寸、位置、字体、行高、颜色、父子关系、Auto Layout 和素材版本。不要仅按旧截图猜测，也不将旧本地稿整块覆盖回去。

建立最小变更清单：

| 项目 | 最新依据 | 受影响位置 | 实现与验收 |
| --- | --- | --- | --- |
| FAQ 字号与颜色 | 当前手调稿 | 首页 / 价格、相关语言和断点 | 更新排版，检查展开状态 |
| 产品组合位置 | 当前 hero 节点 | 桌面与手机画面 | 保留指定比例，检查整体构图 |
| 素材替换 | 用户确认文件 | header、footer、登录、菜单、favicon | 更新并核对版本与裁切 |

共享规则应同步，用户独立调整的断点则按其意图处理。代码中可运行的行为可能比设计稿更详细，回写设计时补相关状态，不为一致而删掉已有必要功能。

按属性合并，不把“最新设计”理解为整块覆盖。例如用户说“位置按我手调的，尺寸保持你缩小后的”，本轮分别记录：位置取当前节点；宽高与整体比例取已确认缩小版；其余字体、素材与交互沿用现有约定。同步后在同一画面验证位置与尺寸同时成立。

将受影响位置逐项标记为“已同步 / 不适用 / 待处理”，至少包含设计稿和代码两层；页面、语言、断点、默认 / 展开 / 滚动状态按本轮选择。不能只写“中英文已同步”，却只更新桌面首页。

## 3. 控制本轮改动

先修来源，再修表现：旧素材、错误组件、固定宽度、静态页面、缓存和旧部署分别诊断。用全局字号缩小或 overflow:hidden 掩盖局部约束通常会转移问题。

完成一组相关反馈后，检查本轮改动与已有约定，保留无关用户修改。不要因一条审美建议擅自重排整个页面或改变业务逻辑。

同一反馈第二次出现时，先查修复是否真正生效：实际字体 / 样式与素材、组件的其他实例、动态加载路径和部署版本。扩大到受影响的同类实例核对，再报告修正；不能再次只凭局部代码或静态截图宣称解决。

## 4. 分层验收

| 层 | 主要检查 | 不能单独证明什么 |
| --- | --- | --- |
| 内容与素材 | 标题、事实、图片、品牌和链接正确 | 交互或数据真实可用 |
| 视觉与布局 | 整页节奏、局部细节、断点、真实字体 | 表单已保存、登录已接通 |
| 行为与数据 | 进入、切换、提交、返回、发布和刷新 | 生产域名已部署当前版本 |
| 工程 | 相关 lint、类型、测试和构建 | 页面观感和上线结果 |
| 交付环境 | 版本、资源、路由、域名与实际任务流程 | 未测地区或私有数据状态 |

选择与变更相关的状态和设备，避免无差别重复全量检查。视觉修改需要实际画面检查；若用户暂停浏览器、截图或正在演示，遵守约束，使用允许的独立会话、已有证据或其他检查，不接管其浏览器。

发现无法验证的环节，继续完成无关工作并如实标注。不把工具受限误写成网站功能失败，也不把本地模拟测试写成线上通过。

证据截图先确认实际视口、所在区块和控件状态，保存后查看图片，不只凭文件名判断。平滑滚动、弹窗 close 或异步状态尚未稳定时，等待对应 UI 条件再读取；不能在执行一次“回到顶部”后立刻把仍在页尾的截图命名为首屏，也不能将暂态误判为最终结果。

## 5. PR 与代码交付

按用户和 repo 约定确定作者身份、干净基线、实现目录和 PR 关系。新建 PR 后检查真实 base、改动范围与作者；不要把同事基线或其他分支修改混入本次 UIUX 变更。

PR 说明写最终问题、可见结果、相关预览与验收步骤。用户要求关联任务时使用真实 PR 链接，并确认关联结果。调用工具创建 PR 后按当前环境要求附加到本 chat。

后续修改核对当前 head；旧提交 CI 通过不代表新提交通过。不同地区 PR 是否独立交付按依赖决定，合并授权沿用当前明确约定，不自动跨到未授权 PR。

反馈到来时原 PR 已合并，后续修正基于当前目标分支建立清楚的新提交 / PR，并关联原交付；不要继续把已合并 PR 当作待合并入口。用户优先要中文演示或先合并一部分时，先交付对应可检查版本并明确其他版本进度，不让无依赖工作相互阻塞。

## 6. 部署后再核对一次

任务包含上线或合并后交付时，核对：

1. 正确账户、项目、分支与预期版本。
2. 实际构建是否执行，成功、失败、被取消或被跳过的原因。
3. 部署产物与目标域名当前指向。
4. 对外入口是否能按约定公开访问或经过适当保护。
5. 相关资源、路由、导航和关键业务流程。
6. CMS / 数据库中的已发布版本是否生效，是否仍命中旧静态内容或缓存。

“PR 已合并”与“域名已更新”分别报告。没有当前可用预览时，不把已清理链接或旧 staging 当作最新版交付。静态页面可用文件或内容比对辅助确认；动态页面使用版本标识、部署记录和相关数据行为验证。

平台权限不足时定位具体权限。登录成功、能看见团队与能创建项目、绑定域名是不同能力。不要把工具连接失败等同于账号内不存在资源。

## 7. 交付与维护

按任务交付设计节点、源码、PR、预览或正式链接，并说明完成阶段、必要检查和剩余缺口。源码包保留运行与维护所需文件，排除密钥、环境文件、登录状态、无关缓存和依赖目录。

有实际维护需求时，在项目已有文档记录构建命令、内容来源、发布方式和回滚线索。只保留可用的当前入口；临时测试数据按约定清理或保留，不擅自删除用户要求查看的测试产品。

最终回复优先给用户可查看的结果，区别“设计完成、实现完成、UI 预览通过、接口接通、已合并、已上线”。不要把尚未完成的任一阶段压缩成一句“全部完成”。
