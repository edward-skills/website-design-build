# 网站设计与搭建

把业务资料、已有品牌资产和用户反馈，转成可编辑的设计、可运行的网站以及可核验的交付结果。适用于新建网站、现有网站改版、Figma 到代码，以及持续反馈迭代。

“独立站”是网站形态；B2B 询盘是其中一种业务模式。先确认网站服务的客户和目标动作，再选择页面结构与实现方式。

## 跨 Agent 使用

完整安装本目录，以 `SKILL.md` 为入口，按需读取引用文件；相对链接以所在文档的目录为基准，不以网站项目的工作目录为基准。`agents/openai.yaml` 是可选的宿主 UI 元数据，其他 Agent 可以忽略，不影响正文工作流。

使用当前宿主已有的文件、代码执行、设计和浏览器能力；本 skill 不依赖指定模型、Codex、Figma 或某家托管服务。选择实现后才确定项目运行依赖。没有浏览器时仍完成源码与可执行检查，并如实标注视觉和交互未实测；没有认证、支付或外部写入能力时按相应模块处理，不伪造完成。安装或调用本 skill 不增加外部账户权限。

## 快速开始：用户给内容，就开始做

用户提供品牌介绍、网站文案、产品信息、素材包、现有网站或参考中的任意已有信息，都可以作为起点。例如：

> 我们做婚礼仿真花出口，客户是海外批发商。用这些图片做一个英文独立站，方便客户询盘。
>
> 这是我们的 SaaS 产品介绍和截图，帮我做首页、价格页和登录页，沿用现有品牌色。
>
> 帮我把这份内容和素材做成一个好看的品牌官网，先给我可打开的网页。

收到后由 agent 自行完成：读取已给资料 → 提炼目标与主动作 → 组织页面 → 选择视觉方向 → 按任务制作设计或可运行网页 → 检查并交付。用户不需要知道模块名称、填写模板、提供完整 sitemap 或指定技术栈。

首次只有少量品牌信息和素材时，先读 [少量输入直接出稿](references/first-build.md)，从素材分工、五项视觉决策和最小实现推进到浏览器实测，不预读全部模块。

- **默认沿用已有资料与项目。** 已有站点、设计系统、品牌、代码和素材优先复用。新项目从内容与资产推导合适方向，不先要求用户挑字体、组件库或部署平台。
- **只问影响结果的问题。** 信息能推断就先做；确实无法确定目标用户或主要动作时，集中简短询问，并继续素材整理等独立工作。缺少最终社媒、视频或联系方式不阻止其余页面。
- **按请求交付。** “设计并搭建 / 做网页”默认推进到可运行页面和可访问预览；“先看设计 / 先确认框架”就完成该阶段。Figma 作为用户选择的交付方式，不自动增加一道确认门槛。
- **区分合理假设与事实。** 可先决定版式、图片用途和文案草案；不编造客户、认证、业绩、价格或产品能力。待补事实放在交付记录；确需占位的预览区域不伪造业务成功。
- **控制用户负担。** 首次更新用简短语言说明理解与行动，完成后给可打开结果和少量关键说明。内部 brief、规格与验收记录由 agent 维护，只在对用户有用时展示。

## 先选择工作路径

| 当前任务 | 直接从哪里开始 | 工作深度 |
| --- | --- | --- |
| 新站或整体改版 | 资料与范围 → 内容 → 视觉 → 实现 | 执行需要的完整链路 |
| 已确认设计，开始实现 | 读取最新设计与已有代码 | 补齐缺失状态和布局约束，保留现有功能 |
| 用户在 Figma 手调后要求同步 | 读取最新节点，建立变更清单 | 只展开受影响的页面、断点和语言 |
| 字号、间距、图标等明确局部修改 | 检查实际来源后修改 | 不重做 brief，不强制增加设计稿或新测试 |
| 增加留资、产品发布或轻量后台 | 检查现有接口与数据来源 | 明确数据闭环后实现，按需加载后台模块 |
| 预览、合并或上线验收 | 检查版本、环境和真实入口 | 沿用已有授权，核实对应的交付状态 |

只在用户要求阶段确认，或缺失信息会改变方案时停在确认点。用户已确认范围和方向后，继续完成下一步，不重复请求许可。设计确认、发布和合并按当前任务的约定执行，不额外创建统一的审批流程。

## 执行原则

1. **读取完整证据。** 文档正文、表格、截图、备注、用户手调和运行中的产品各有用途；不要只读摘要后自行补造内容。
2. **保留已确认的选择。** 品牌标识、色系、字体、页面数量、现有业务逻辑和用户正在使用的浏览器约束都进入任务记录。明确纠正覆盖旧要求。
3. **将审美描述拆成可操作变量。** “高级”需要落到构图、比例、层级、字重、留白、颜色、材质或运动方式，并通过实际画面检查。
4. **让产品表达准确。** 使用真实产品 UI 与素材做选择、裁切和加工；简化展示不能变成虚构能力或误导性的操作入口。
5. **按用途做响应式。** 营销展示画面可整体等比缩放，真实按钮、输入框、导航与正文按内容和操作要求自适应。
6. **让 CTA 与结果一致。** 链接、登录、购买、提交和保存对应真实动作；UI 预览、待接入接口和真实可用流程分别记录。
7. **将反馈同步到所有受影响位置。** 同步最新设计、代码、页面、断点和语言；不覆盖用户无关手调，不将一次局部反馈推广成全站重做。
8. **以交付环境验证完成。** 构建成功、PR 通过、合并成功、部署就绪、域名更新和业务可用分别确认。

这些原则不指定固定风格。字体、配色、深浅底节奏、轮播控件、FAQ 默认状态、语言策略和技术平台都按项目决定。已有素材的整理与应用在范围内；Logo 重设计、3D/IP 创作和角色延展不在本 skill 范围内。

具体用户反馈作为可检索的处理方法：字号与按钮重量分开调整；场景图保持同一布局语法；装饰组缩放后收拢位置；动效分别验证轮廓、颜色、模糊和颗粒；用户手调按属性合并。新用户没有这些偏好时按其内容和品牌判断，不继承历史项目的字体、图形、配色、域名或账号。

## 主工作流

### 1. 锁定本次任务

识别目标客户、主要动作、页面范围、已有项目、需保留的功能，以及用户当前要看的是框架、设计、代码还是部署结果。只有影响方案的未知项才向用户提问；其余使用可说明的合理假设继续。

整体项目可在内部使用 [项目 brief 模板](assets/templates/project-brief.md)，从用户已给资料填写，不能要求用户补齐所有字段才开始。局部修改只在现有任务记录中补充，不生成成套空文档。

### 2. 组织信息与用户路径

从原始资料建立“用户问题 → 内容与证据 → 页面位置 → 下一步动作”的对应关系。每个 section 有明确目的；标题优先让访客理解内容。压缩重复内容时保留用户指定的关键区块和流程说明。

### 3. 确立视觉与实现约束

拆解参考的具体机制，读取最新品牌和设计稿，优先确定首屏、关键产品画面与整页节奏。记录真实交互和装饰画面的区别、文字与图片比例、布局关系和移动端处理方式。

需要交接复杂 section 时，使用 [section 规格模板](assets/templates/section-spec.md)，不要求所有简单区块都填写。

### 4. 做成可检查的设计或代码

按用户约定先设计或直接实现。设计稿保留所需可编辑性；代码复用现有组件、路由和业务能力。用户只要求 UIUX 时不改写账户、权限、计费和产品数据语义。

调用 Figma、网站构建、浏览器、代码托管或部署工具前，遵守当前工具文档和相关技能的使用要求。本 skill 提供方法与验收标准，不替代平台 API 文档，也不指定必须可用的外部工具。

### 5. 迭代并验证

先确认反馈对应的设计节点、预览和版本，再修改。明确哪些要求被替代，检查共享位置，完成对应的视觉或行为验收。测试深度按变更影响选择，不能用构建通过代替视觉检查，也不用为低影响样式修改编写镜像测试。

### 6. 完成约定的交付

用用户可访问的入口验收。若任务包括上线，确认合并后的实际部署、域名和必要的数据状态；若只要求设计或本地实现，就交付该阶段，不自行扩大到发布。

多轮项目可使用 [迭代与交付记录模板](assets/templates/delivery-ledger.md)，复用 issue、PR 或已有项目文档承载，避免重复维护。

## 完成判定

- 请求中的页面、内容和交互已覆盖；未做项有明确原因。
- 用户只给内容、品牌与素材时，也能得到与请求阶段相符的实际结果，没有被要求先掌握本流程。
- 用户最新确认的设计与约束仍成立，相关断点和语言已同步。
- 真实操作能到达承诺的结果；缺失资源和待接入能力如实说明。
- 相应的构建、视觉、任务流程或线上检查有当前版本证据。
- 最终回复给出结果、可用链接和必要限制；详细检查留在项目已有记录中。
